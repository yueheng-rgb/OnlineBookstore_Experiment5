## 3:00—4:10 系统设计和技术架构

【屏幕操作：展示项目整体目录结构，特别突出 src/main/java/com/onlinebookstore/ 下的分层】

接下来介绍系统的技术架构。整个项目采用经典的分层架构，这也是 Spring Boot 项目最常用的组织方式。

最上层是 Controller 层，负责接收 HTTP 请求。我写了 4 个控制器：BookController 处理图书相关接口，CartController 处理购物车，OrderController 处理订单，UserController 处理用户注册和登录。

中间是 Service 层，这里写所有的业务逻辑。比如 BookService 负责图书的增删改查和库存管理，OrderService 处理订单创建——包括从购物车生成订单、扣减库存、在一个数据库事务中完成这些操作，保证数据不会出现不一致。

再往下是 Repository 层，用的是 Spring Data JPA，只需要定义接口，Spring 会自动生成基本的数据库操作方法。

最底层是 Entity 层，对应数据库的 6 张表：Book 图书表、User 用户表、Cart 购物车表、CartItem 购物车明细表、Order 订单表、OrderItem 订单明细表。

在数据库方面，默认使用 H2 内存数据库，这样不需要安装任何外部数据库就可以直接运行和测试。同时我也配置了 MySQL 和 Redis 的可选方案——通过 Spring Profile 切换即可。

系统启动时会自动初始化 12 本图书和 3 个测试用户，这些数据通过 DataInitializer 组件在项目启动时写入。

## 4:10—5:00 编码实践与开发

【屏幕操作：在 IDE 或文件浏览器中展示核心 Service 代码，特别是 OrderService.createOrder 方法】
【路径：src\main\java\com\onlinebookstore\service\OrderService.java】

在编码阶段，我重点实现了几个核心业务流程。

第一个是订单创建流程。用户把书加入购物车之后，提交订单时系统会做三件事：先检查购物车是否为空、每本书的库存是否足够；然后生成订单编号、创建订单明细、计算总金额，同时扣减对应图书的库存；最后清空购物车。这三个步骤在同一个数据库事务中完成——要么全部成功，要么全部回滚，这样就不会出现库存扣了但订单没生成的情况。

第二个是取消订单的库存恢复。当用户或者管理员取消一个订单时，系统会把订单状态改为"已取消"，同时把之前扣减的库存数量加回去。这里面有一个细节需要特别注意：库存扣减和恢复操作都需要清除 Spring 的缓存。如果不做缓存清除，下次查询图书时拿到的还是旧的库存数据，就会出现数据不一致的问题。我在 BookService 中专门加了 CacheEvict 注解来解决这个问题。

## 5:00—6:00 异常处理与统一响应

【屏幕操作：展示 GlobalExceptionHandler.java 和 ErrorResponse.java】
【路径：src\main\java\com\onlinebookstore\exception\】

在开发过程中，我特别重视异常处理的规范性。所有接口的异常响应都使用统一的 ErrorResponse 格式，包含五个字段：timestamp 是异常发生的时间、status 是 HTTP 状态码、errorCode 是业务错误码、message 是中文错误说明、path 是出错的请求路径。

我定义了 7 种业务错误码：BOOK_NOT_FOUND 代表图书不存在，返回 404；ORDER_NOT_FOUND 代表订单不存在，也返回 404；INSUFFICIENT_STOCK 代表库存不足，返回 400；VALIDATION_FAILED 代表参数校验失败，返回 400 并附带具体是哪个字段出了问题；USER_NOT_FOUND 代表用户不存在；CART_NOT_FOUND 代表购物车为空；INTERNAL_SERVER_ERROR 代表服务器内部错误，返回 500。

这种统一格式的好处是，前端或者调用方只需要检查 errorCode 就能知道出了什么问题，不用去解析不同的响应结构。

【屏幕操作：展示 Jenkinsfile 和 docker-compose.yml】

在部署准备阶段，我做了三件事。

第一件，编写了 Jenkins Pipeline 的配置文件。Jenkinsfile 定义了 8 个阶段的自动化流水线：代码检出、编译、单元测试、JaCoCo 覆盖率报告、打包、Docker 镜像构建、部署到测试环境、以及归档构建产物。这意味着每次代码提交之后，Jenkins 可以自动完成从编译到部署的全过程。

**Q1：为什么选择 Spring Boot？**

Spring Boot 是 Java 生态中最主流的企业级开发框架，它提供了自动配置、内嵌服务器和丰富的生态集成。对于这个实验项目来说，使用 Spring Boot 可以快速搭建一个完整的 Web 应用，同时 Spring Data JPA 简化了数据库操作，Spring Cache 提供了缓存支持，这些在实验中都用到了。

**Q2：为什么默认使用 H2 数据库？**

H2 是一个 Java 写的内存数据库，不需要安装任何外部数据库软件。项目启动时自动创建表结构，停止时数据清空，非常适合开发、测试和实验演示。而且在 pom.xml 中已经配置了 MySQL 的依赖，通过修改 Spring Profile 就可以切换到 MySQL。

---

**Q3：MySQL 如何切换？**

项目已经准备好了 MySQL 的配置文件 application-mysql.yml。切换只需要两步：第一步，修改 application.properties 中的 spring.profiles.active 从 h2 改为 mysql；第二步，在 application-mysql.yml 中配置正确的 MySQL 连接地址、用户名和密码。如果使用 docker-compose.yml，MySQL 容器的配置也已经写好了。

---

**Q4：Redis 有什么作用？**

Redis 在这个项目中用作二级缓存。默认情况下 Spring 使用简单的内存缓存（ConcurrentHashMap），在高并发场景下，使用 Redis 作为集中式缓存可以带来两个好处：一是多个应用实例可以共享缓存数据，二是缓存数据不会因为应用重启而丢失。JMeter 的两阶段压测就是为了对比无缓存和 Redis 缓存的性能差异。

---

**Q5：Redis 不可用怎么办？**

项目设计为 Redis 是可选的。默认的 H2 profile 使用的是 Spring 的 Simple Cache，不依赖 Redis。nocache profile 则完全关闭缓存。所以即使 Redis 不可用，系统也能正常运行，只是缓存加速的功能没有了。这就是为什么我设计了三种配置文件——h2、nocache 和 redis——来适应不同的运行环境。

---

**Q6：为什么下单需要事务？**

下单操作涉及多个数据库操作：创建订单、创建订单明细、扣减多本书的库存、清空购物车。这些操作必须在同一个事务中完成——要么全部成功，要么全部失败回滚。如果不使用事务，可能出现库存已经扣了但订单没创建成功的情况，导致数据不一致。在 Spring 中，@Transactional 注解确保了整个方法在事务中执行。

---

**Q7：为什么取消订单要恢复库存？**

因为下单时已经扣减了库存——那两本书从可售库存中划走了。如果用户取消订单，这些书应该重新变成可售状态。如果不恢复，就会出现"订单取消了但书也没了"的情况。恢复库存的同时也清除了缓存，保证后续查询拿到的是正确的库存数量。

---

**Q8：为什么要使用 DTO？**

DTO 是数据传输对象。使用 DTO 的原因有三个：第一，把 Entity 和 API 接口解耦——Entity 是数据库的映射，DTO 是接口的契约，两者独立变化；第二，可以控制哪些字段暴露给前端——比如 User 的 password 字段通过 @JsonIgnore 隐藏，API 响应中不会出现密码；第三，可以在 DTO 上添加独立的校验注解，不污染实体类。

---

**Q9：Swagger 是什么？**

Swagger 也就是 OpenAPI，是一个 API 文档工具。我在项目中集成了 SpringDoc OpenAPI，启动应用后访问 swagger-ui.html 页面，就能看到所有接口的列表、请求参数和响应格式。每个接口旁边都有一个"Try it out"按钮，可以直接在页面上测试，不需要用 Postman 或者 curl。这对于前后端联调非常有帮助。

---

**Q10：JaCoCo 是什么？**

JaCoCo 是 Java 代码覆盖率工具。它会在运行单元测试的时候记录哪些代码行被执行了、哪些分支被覆盖了，然后生成一个可视化的 HTML 报告。绿色表示被覆盖，红色表示未被覆盖。这个项目执行 mvnw.cmd clean verify 之后，可以在 target/site/jacoco/index.html 中查看详细的覆盖率报告。

---

**Q11：注释覆盖率和测试覆盖率有什么区别？**

测试覆盖率，也就是 JaCoCo 覆盖率，衡量的是代码被单元测试执行的程度——你的测试跑到了多少行代码、覆盖了多少分支。注释覆盖率是另一个概念，它是用自定义脚本统计的——注释行数除以总代码行数，衡量的是代码的可读性和文档完整度。两者是完全不同的指标。这个项目的 JaCoCo 指令覆盖率是 65.9%，注释覆盖率是 43.8%。

---

**Q12：Jira 中的 Epic、Story、Task 是什么关系？**

Epic 是最大的工作单元，代表一个完整的功能模块，比如"图书管理"。一个 Epic 下面有多个 Story，Story 是可以独立交付的用户故事，比如"图书搜索与库存管理"。Story 下面再拆成具体的开发 Task，比如"实现图书基本 CRUD 功能"。Parent 字段通过数字 ID 来关联父子关系——Story 的 Parent 指向 Epic，Task 的 Parent 指向 Story。

**Q13：为什么 Jira 里没有全部导入 35 条？**

CSV 导入文件已经准备好了，包含全部 35 条任务。但是在实际导入 Jira Cloud 时，不同版本的导入器对字段名称有不同要求——新版用 Work item ID 和 Work type，旧版用 Issue ID 和 Issue Type，而且字段映射的下拉选项中可能找不到对应的字段名。我已经为不同版本生成了多份兼容的 CSV 文件，在实际有 Jira 的环境中可以根据当前界面的字段名称选择对应的文件导入。

**Q14：Jenkinsfile 有什么作用？**

Jenkinsfile 是 Jenkins 的流水线配置文件，它把整个构建部署流程写成代码。这个项目的 Jenkinsfile 定义了 8 个阶段：代码检出、编译、单元测试、JaCoCo 覆盖率报告、打包、Docker 镜像构建、部署到测试环境和归档。只要在 Jenkins 中创建一个 Pipeline 任务指向这个 Jenkinsfile，每次代码提交后 Jenkins 就会自动执行这 8 个阶段。

**Q15：JMeter 测试比较哪些指标？**

JMeter 的两阶段压测主要对比四个核心指标：平均响应时间——用户请求的平均耗时；P99 响应时间——百分之九十九的请求在多长时间内完成；吞吐量——每秒可以处理多少个请求；以及错误率。通过无缓存和 Redis 缓存两种模式的对比，可以量化缓存对系统性能的提升效果。每个模式各包含 3 个并发级别：10、50 和 100 线程。

**Q17：如果库存同时被多人购买，怎么避免超卖？**

目前项目把库存校验和扣减放在同一个事务中，这保证了单个请求内部的原子性。但在极高并发场景下，两个请求可能同时读到库存为 10，都认为自己可以下单。更严格的解决方案是使用数据库的行级锁——在扣减库存时使用 UPDATE books SET stock = stock - ? WHERE id = ? AND stock >= ? 这样的 SQL，数据库会在更新时自动加锁，确保不会超卖。此外还可以使用 Redis 分布式锁或者消息队列来削峰，但这些属于高并发架构的范畴，超出了本实验的范围。

**Q18：统一异常响应有什么好处？**

统一异常响应格式最大的好处是让前端和调用方的工作变得简单——不管是什么错误，响应的 JSON 结构都是一样的，包含 timestamp、status、errorCode、message 和 path。前端只需要检查 errorCode 字段就能知道出了什么问题，不需要针对不同的异常类型写不同的解析逻辑。另外，这种格式也方便在日志系统中检索和分析错误模式。
